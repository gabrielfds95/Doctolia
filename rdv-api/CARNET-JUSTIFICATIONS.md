## Architecture / Modèle

**Q : Pourquoi les IDs sont en `Long` et pas `int`/`Integer` ?**
R : `Long` supporte des valeurs jusqu'à ~9,2 × 10¹⁸ (vs ~2,1 milliards pour `int`), suffisant pour ne jamais craindre un dépassement même avec une base de données qui grossit sur des années. C'est aussi le type que génère nativement `GenerationType.IDENTITY` avec la plupart des SGBD (auto-increment sur `BIGINT`). Utiliser `int` obligerait en plus à gérer l'auto-boxing différemment et interdirait `null` (utile pour représenter "pas encore persisté").
Fichiers : [User.java](src/main/java/com/rdvmedic/rdv_api/model/User.java), [Slot.java](src/main/java/com/rdvmedic/rdv_api/model/Slot.java)

**Q : Pourquoi `@Inheritance(strategy = JOINED)` et pas `SINGLE_TABLE` ?**
R : `JOINED` crée une table par sous-classe (`users`, `doctors`, `patients`) reliée par clé étrangère sur l'id. Avantage : chaque table ne contient que ses colonnes propres, donc pas de colonnes `NULL` en masse (ex. `ssn` n'existe pas dans `doctors`). `SINGLE_TABLE` aurait mis toutes les colonnes de toutes les sous-classes dans une seule table `users`, avec des `NULL` partout et un risque de collision de contraintes (ex. `unique` sur `license_number` qui n'a de sens que pour un médecin). Le compromis de `JOINED` est un `JOIN` SQL supplémentaire à chaque lecture — acceptable ici car pas de volumétrie critique.
Fichiers : [User.java](src/main/java/com/rdvmedic/rdv_api/model/User.java), [Doctor.java](src/main/java/com/rdvmedic/rdv_api/model/Doctor.java), [Patient.java](src/main/java/com/rdvmedic/rdv_api/model/Patient.java)

**Q : Pourquoi `@SuperBuilder` sur `User`/`Doctor`/`Patient` et pas `@Builder` ?**
R : `@Builder` (Lombok) génère un builder qui ne connaît que les champs de sa propre classe — il ignore les champs hérités de la superclasse. Sur une hiérarchie (`Doctor extends User`), `Doctor.builder().username(...)` ne compile pas avec `@Builder` car `username` est dans `User`. `@SuperBuilder` génère un builder qui chaîne l'appel au builder parent, donc `Doctor.builder().username(...).speciality(...).build()` fonctionne. `Slot` et `Document` n'héritent de rien → `@Builder` simple suffit pour eux.
Fichiers : [User.java](src/main/java/com/rdvmedic/rdv_api/model/User.java), [Doctor.java](src/main/java/com/rdvmedic/rdv_api/model/Doctor.java)

## Sécurité

**Q : Pourquoi JWT et pas une session serveur classique ?**
R : Le backend sert à la fois une app Angular web et une app mobile React Native — deux clients qui n'ont pas de notion native de "cookie de session" partagée. Un JWT est auto-porteur : il contient l'identité (`sub`), l'id BDD (`userId`) et les rôles (`roles`), signé en HMAC-SHA256. Le serveur n'a donc rien à stocker (`SessionCreationPolicy.STATELESS`) — chaque requête est vérifiable indépendamment avec juste la clé secrète. C'est aussi ce qui permet de scale horizontalement sans partager un store de sessions entre instances.
Fichiers : [JwtTokenProvider.java](src/main/java/com/rdvmedic/rdv_api/security/JwtTokenProvider.java), [SecurityConfig.java](src/main/java/com/rdvmedic/rdv_api/config/SecurityConfig.java)

**Q : Pourquoi CSRF est désactivé (`csrf.disable()`) ?**
R : CSRF protège les flux authentifiés par cookie de session, où le navigateur envoie automatiquement le cookie sur toute requête (même cross-site). Ici, l'authentification se fait via un header `Authorization: Bearer <token>` que le navigateur n'attache jamais automatiquement — un site tiers ne peut pas forcer son envoi. La protection CSRF n'a donc pas d'objet dans une architecture JWT stateless.
Fichier : [SecurityConfig.java:72](src/main/java/com/rdvmedic/rdv_api/config/SecurityConfig.java#L72)

**Q : En quoi Spring Data JPA protège contre l'injection SQL ?**
R : Toutes les requêtes du projet passent soit par des méthodes dérivées (`findByUsername`, `findByDoctorId`...) soit par le JPQL généré automatiquement — jamais par de la concaténation de chaînes SQL. Spring Data transforme ces appels en requêtes **préparées** (`PreparedStatement`), où les valeurs (username, id...) sont passées comme paramètres liés (`?`), jamais interpolées dans le texte de la requête. Un attaquant ne peut donc pas injecter de SQL via un champ texte, car ce champ est toujours traité comme une donnée, jamais comme du code SQL.
Vérifié : aucune occurrence de `createNativeQuery`, `createQuery` avec concaténation, ni de `@Query` dans tout le code (`grep` sur `src/main/java`).

**Q : Pourquoi BCrypt et pas MD5/SHA-256 nu ?**
R : MD5/SHA sont des fonctions de hachage rapides, conçues pour l'intégrité de données, pas pour les mots de passe — un attaquant peut tester des milliards de combinaisons par seconde (brute-force/rainbow tables). BCrypt est volontairement lent (facteur de coût configurable, 10 rounds par défaut) et **salé automatiquement** : deux utilisateurs avec le même mot de passe obtiennent des hashs différents, ce qui neutralise les rainbow tables.
Fichier : [SecurityConfig.java:46-49](src/main/java/com/rdvmedic/rdv_api/config/SecurityConfig.java#L46-L49)

**Q : Pourquoi un DTO `PublicSlotDTO` séparé plutôt que réutiliser `SlotDTO` en filtrant le patient au cas par cas dans le controller ?**
R : `SlotDTO` embarque un `PatientDTO` complet (NIR, téléphone, adresse). Le risque avec "filtrer au cas par cas" (ex. mettre `patient = null` avant de sérialiser) est qu'un futur développeur ajoute un endpoint public en réutilisant `SlotDTO::fromEntity` sans y repenser, et réintroduise la fuite. En créant un type distinct qui **ne possède structurellement pas** le champ patient (`PublicSlotDTO` n'a même pas d'attribut `patient`), l'omission devient impossible à l'insu du développeur — c'est le compilateur qui garantit l'absence de la donnée, pas une discipline de code. C'est le principe de *data minimization* du RGPD appliqué au niveau du type : on ne peut pas fuiter une donnée qui n'existe pas dans l'objet.
Fichiers : [PublicSlotDTO.java](src/main/java/com/rdvmedic/rdv_api/dto/PublicSlotDTO.java), [AUDIT-SECURITE.md](AUDIT-SECURITE.md) (faille 1)

**Q : Pourquoi garder `GET /slots` et `GET /doctors/{id}/slots` publics au lieu de tout mettre derrière une authentification ?**
R : Ces deux endpoits ont un cas d'usage légitime avant connexion — comme sur Doctolib, un visiteur doit pouvoir voir les disponibilités d'un médecin (et donc décider de s'inscrire) sans être obligé de créer un compte au préalable. Le vrai problème n'était pas que ces endpoints soient publics, mais **ce qu'ils exposaient** en étant publics. La bonne réponse à "cette donnée est trop sensible pour être publique" est de retirer la donnée sensible du DTO, pas de fermer l'accès à une fonctionnalité qui doit rester accessible.
En revanche, `GET /slots/{idDoctor}/{idPatient}` (requête ciblée sur un patient précis) n'a **aucun** cas d'usage anonyme légitime — il a donc été retiré de `permitAll()` et nécessite désormais un token (`403` sans authentification).
Fichier : [SecurityConfig.java](src/main/java/com/rdvmedic/rdv_api/config/SecurityConfig.java)

**Q : Comment l'ownership est-il vérifié sur `cancelSlot`/`updateSlotReason`/`completeSlot`, et pourquoi 403 plutôt que 404 quand le slot appartient à quelqu'un d'autre ?**
R : Le controller extrait l'id de l'utilisateur connecté depuis le `SecurityContext` (`currentUser.getId()`, alimenté par le JWT via `JwtAuthenticationFilter`) — jamais depuis un paramètre de la requête, donc infalsifiable côté client. Cet id est transmis au service, qui compare `slot.getPatient().getId()` (ou `.getDoctor().getId()`) à cet id, et lève une `ResponseStatusException(FORBIDDEN)` sinon.
Le choix de **403** plutôt que **404** est délibéré : le créneau `{id}` existe bel et bien, ce n'est pas une question de "ressource introuvable" mais de "vous n'avez pas le droit d'agir dessus" — HTTP distingue les deux (404 = la ressource n'existe pas, 403 = elle existe mais l'accès est refusé). Certains évitent volontairement le 403 au profit du 404 pour ne pas confirmer l'existence de l'id à un attaquant qui teste des ids au hasard (énumération) — un compromis possible pour une version plus durcie, mais pas retenu ici pour rester explicite et facile à déboguer/expliquer.
Fichiers : [SlotService.java](src/main/java/com/rdvmedic/rdv_api/service/SlotService.java) (`requireOwnerPatient`, `requireOwnerDoctor`), [SlotController.java](src/main/java/com/rdvmedic/rdv_api/controller/SlotController.java), [AUDIT-SECURITE.md](AUDIT-SECURITE.md) (faille 2)

**Q : Qu'est-ce que le "deny-by-default", et pourquoi c'est important en sécurité ?**
R : C'est le principe qui dit que par défaut, un accès doit être **refusé**, et qu'il faut explicitement ouvrir chaque route à qui en a besoin — plutôt que l'inverse (tout ouvrir par défaut et fermer au cas par cas). Dans `SecurityConfig`, la dernière règle `.anyRequest().authenticated()` sert de filet : toute route qu'un développeur oublierait de configurer explicitement exige au moins d'être connecté (jamais publique par accident). Mais "être connecté" n'est pas "avoir le bon rôle" : avant ce correctif, `DELETE /doctor/{id}` n'avait pas de règle dédiée, donc tombait dans ce filet — un simple patient connecté pouvait supprimer un médecin, simplement parce que personne n'avait pensé à écrire une règle spécifique. Le correctif ajoute une règle explicite par action sensible (`hasRole("ADMIN")`, `hasRole("DOCTOR")`...), pour que le filet générique ne soit jamais le seul rempart sur une action qui touche à des comptes ou des données d'autrui.
Fichiers : [SecurityConfig.java](src/main/java/com/rdvmedic/rdv_api/config/SecurityConfig.java), [AUDIT-SECURITE.md](AUDIT-SECURITE.md) (faille 3)

**Q : Qu'est-ce que le "mass assignment", et pourquoi `@RequestBody Patient`/`@RequestBody Slot` y sont exposés ?**
R : Le mass assignment survient quand un endpoint désérialise directement le JSON du client vers une entité qui a plus de champs que ce que le client devrait pouvoir renseigner. Jackson (le désérialiseur JSON de Spring) remplit **tous** les champs présents dans le JSON qui correspondent à un setter de la classe cible — il ne fait aucune distinction entre "champ métier attendu" et "champ interne sensible". Avec `@RequestBody Patient`, un client pouvait donc glisser `"roles": [...]` ou `"enabled": true` dans sa requête ; avec `@RequestBody Slot`, un client pouvait fournir un `id` qui, combiné au comportement de `JpaRepository.save()` (id déjà existant en base → UPDATE au lieu d'INSERT), permettait de cibler et modifier un enregistrement d'un autre utilisateur.
La correction structurelle est de ne **jamais** binder le JSON client directement sur une entité JPA : un DTO d'entrée (`SlotCreateDTO`, `PatientCreateDTO`) ne déclare que les champs que le client a le droit de fournir — les champs sensibles (id, rôle, statut) n'existent tout simplement pas dans le type, donc aucun JSON ne peut les atteindre, quoi que le client envoie.
Fichiers : [SlotCreateDTO.java](src/main/java/com/rdvmedic/rdv_api/dto/SlotCreateDTO.java), [PatientCreateDTO.java](src/main/java/com/rdvmedic/rdv_api/dto/PatientCreateDTO.java), [AUDIT-SECURITE.md](AUDIT-SECURITE.md) (faille 4)

**Q : Le secret JWT est encore dans `application.properties`, avec une valeur par défaut visible dans le code — c'est un problème ?**
R : Le pattern `app.jwt.secret=${JWT_SECRET:doctolia-secret-jwt-key-...}` est en fait l'idiome standard Spring Boot pour "secret hors du code" : si la variable d'environnement `JWT_SECRET` est définie (ce qu'on fait en prod), elle **remplace** la valeur par défaut — le vrai secret de prod n'a donc jamais besoin d'être écrit ni commité nulle part. La valeur par défaut visible dans le fichier n'est qu'un confort de développement local (permet de lancer `./mvnw spring-boot:run` sans rien configurer).
Le vrai risque n'était pas la présence de ce défaut, mais l'absence de garde-fou si quelqu'un **oublie** de définir `JWT_SECRET` en prod — l'app démarrerait quand même, silencieusement, avec une clé connue de quiconque lit le dépôt public. J'ai ajouté un `@PostConstruct` dans `JwtTokenProvider` qui compare la clé active à la valeur par défaut connue et logue un avertissement bien visible si elles correspondent — l'oubli devient visible dans les logs au lieu d'être silencieux. Le split complet dev/prod via des profils Spring (`application-prod.properties` sans défaut, échec au démarrage si absent) est prévu en Phase 5 (déploiement), car il touche à la configuration multi-environnement, pas seulement à la sécurité applicative.
Fichier : [JwtTokenProvider.java](src/main/java/com/rdvmedic/rdv_api/security/JwtTokenProvider.java)

**Q : Politique de mot de passe — qu'est-ce qui est appliqué et où ?**
R : `@Size(min = 8)` sur le champ `password` de `RegisterRequest` (inscription publique) et de `PatientCreateDTO` (création admin) — dans les deux cas combiné à `@NotBlank`. C'est la seule exigence demandée par le cahier des charges ("longueur mini"). Je n'ai pas ajouté d'exigence de complexité (majuscule/chiffre/caractère spécial) : ce n'était pas demandé, et les études NIST/OWASP récentes déconseillent d'ailleurs les règles de complexité trop strictes (elles poussent souvent vers des mots de passe prévisibles du type "Password1!") au profit de la longueur minimale, qui est justement le critère retenu ici.

**Q : Où en est la protection XSS côté backend ?**
R : Le risque XSS classique (un script injecté dans un champ texte s'exécute chez une autre victime) suppose qu'un serveur **génère du HTML** à partir d'une entrée utilisateur non échappée. Ce n'est pas le cas ici : `rdv-api` est une API JSON pure — aucun endpoint ne renvoie de HTML, aucun template n'est rendu côté serveur (vérifié : aucune dépendance Thymeleaf/JSP dans `pom.xml`). Le rendu revient entièrement au frontend Angular, qui échappe le HTML par défaut dans ses interpolations (`{{ }}`) — un `<script>` stocké en base s'afficherait comme du texte brut, pas comme du code exécuté, sauf si le front utilisait explicitement `[innerHTML]` sans sanitizer (à vérifier côté `rdv_medic_front`, hors périmètre de ce dépôt).
Ce que le backend peut faire en défense en profondeur, déjà fait : borner la longueur des champs texte libres (`slotReason` ≤ 500 caractères via `SlotReasonUpdateDTO`/`SlotCreateDTO`, noms/adresse ≤ 100-255 caractères via les DTO). Je n'ai pas ajouté de bibliothèque de sanitization HTML côté backend (type OWASP Java HTML Sanitizer) : ce serait de la sur-ingénierie pour une API qui ne génère jamais de HTML, et un composant que je ne pourrais pas expliquer simplement à l'oral si le jury demandait pourquoi il est là.

**Q : Pourquoi les 18 tests existants (`@WebMvcTest`) ne pouvaient pas détecter les 4 failles de sécurité, même après correction ?**
R : `@WebMvcTest` charge une tranche minimale du contexte Spring (juste la couche web) et, dans ce projet, ajoute explicitement `excludeAutoConfiguration = {SecurityAutoConfiguration.class, SecurityFilterAutoConfiguration.class}` — la chaîne de filtres Spring Security (dont `JwtAuthenticationFilter` et toutes les règles de `SecurityConfig`) n'est **jamais exécutée** dans ces tests. En plus, chaque service est remplacé par un `@MockBean` — la vraie logique métier (`SlotService.requireOwnerPatient`, etc.) n'est pas non plus exercée. Ces tests vérifient uniquement "le controller sait parser une requête et appeler le bon service" — utile, mais aveugle par construction à tout ce qui concerne l'autorisation. Un test de ce type peut rester vert alors que n'importe qui peut annuler le RDV de n'importe qui : ce n'est pas un bug du test, c'est un choix de portée (tester la couche web isolément) qui ne convient juste pas pour verrouiller des règles de sécurité transverses.
Fichiers : `SlotControllerTest.java`, `DoctorControllerTest.java`, `PatientControllerTest.java`

**Q : Qu'est-ce qui rend `SecurityRegressionTest` capable de détecter ces mêmes failles, concrètement ?**
R : `@SpringBootTest` (sans exclusion) + `@AutoConfigureMockMvc` démarre le contexte Spring **complet** — la vraie chaîne de filtres, donc chaque requête passe réellement par `JwtAuthenticationFilter` puis par les règles de `SecurityConfig`, exactement comme en production. Les tokens utilisés sont obtenus via un vrai `POST /login` (pas un `UserPrincipal` construit à la main comme dans les tests `@WebMvcTest`), donc la validation de signature JWT, le chargement des rôles depuis la base, etc. sont tous réellement exercés. Les services ne sont pas mockés : `SlotService.requireOwnerPatient()` s'exécute pour de vrai. C'est la différence entre tester "le controller délègue bien à X" et tester "un attaquant qui suit exactement ce chemin HTTP est effectivement bloqué".
Fichier : [SecurityRegressionTest.java](src/test/java/com/rdvmedic/rdv_api/security/SecurityRegressionTest.java)

**Q : Comment as-tu prouvé que ces nouveaux tests échouent bien sur l'ancien code, sans juste l'affirmer ?**
R : `git worktree add` permet d'avoir une deuxième copie de travail du même dépôt, pointant sur un autre commit, sans toucher à l'arbre de travail principal. J'ai créé un worktree sur le commit juste avant les 4 correctifs de sécurité, copié uniquement le nouveau fichier de test dedans (le test ne dépend d'aucune classe nouvellement créée — il ne parle qu'HTTP via `MockMvc` — donc il compile aussi bien contre l'ancien code que le nouveau), et lancé `./mvnw test` dans ce worktree isolé. Résultat : 9 échecs sur 11, exactement les tests qui ciblent une vulnérabilité (les 2 qui passent testent un accès légitime, jamais cassé). C'est la preuve empirique — pas juste un raisonnement — que la suite détecte réellement une régression si le code de sécurité est un jour retiré ou modifié par erreur.
Détail complet : [AUDIT-SECURITE.md](AUDIT-SECURITE.md), section "Tests de non-régression sécurité"

**Q : `GET /slots/{idDoctor}/{idPatient}` a-t-il un contrôle d'ownership complet ?**
R : L'endpoint a été **supprimé**, pas corrigé — il n'existe plus. Avant suppression, il exigeait un token (faille 1) mais n'importe quel patient authentifié pouvait encore l'appeler avec l'id d'un autre patient et recevoir son `SlotDTO` complet (NIR inclus). Plutôt que d'ajouter un contrôle d'ownership de plus à maintenir, la question posée a été : *cet endpoint sert-il à quelque chose ?* Recherche dans tout le monorepo (`rdv_medic_front`, `doctolia-mobile`) : aucun appel réel, seule une méthode Angular jamais invoquée le référençait. Fonctionnellement, il fait doublon avec `/patients/me/slots` et `/doctors/me/slots`, qui sont eux correctement scopés par ownership via le JWT. Un endpoint mort qu'on sécurise reste un endpoint de plus à auditer indéfiniment ; un endpoint mort qu'on supprime, c'est une ligne de règle de sécurité en moins à faire vivre. D'où le principe **"réduction de la surface d'attaque"** : face à du code inutilisé et vulnérable, préférer la suppression au correctif quand c'est possible.
Fichiers : [AUDIT-SECURITE.md](AUDIT-SECURITE.md) (section dédiée), [SecurityRegressionTest.java](src/test/java/com/rdvmedic/rdv_api/security/SecurityRegressionTest.java) (`getSlotsByDoctorAndPatient_routeNoLongerExists`)

**Q : Pourquoi le test de "route supprimée" utilise un token valide plutôt que de tester sans token ?**
R : Sans token, la requête est bloquée par `anyRequest().authenticated()` (règle deny-by-default) **avant même** que Spring MVC ne cherche une route correspondante — le client reçoit un 403 que la route existe ou non, ce qui ne prouve rien de spécifique à la suppression. En envoyant un token valide, la requête passe le filtre de sécurité et atteint le dispatcher, qui répond alors 404 précisément parce qu'aucun `@GetMapping` ne correspond. C'est la seule façon d'isoler "la route n'existe plus" de "l'accès est refusé" dans le test.

**Q : `NoResourceFoundException` renvoyait 500 au lieu de 404 — comment ce bug a-t-il été découvert, et pourquoi existait-il ?**
R : `GlobalExceptionHandler` a un `@ExceptionHandler(Exception.class)` générique en dernier recours (pour ne jamais fuiter de stacktrace au client). Spring Security résout le handler le **plus spécifique** applicable à une exception donnée ; comme il n'y avait pas de handler dédié pour `NoResourceFoundException` (l'exception que Spring MVC lève quand aucune route ne correspond à l'URL), c'est le handler générique qui la traitait — et il renvoie toujours 500, quel que soit le type réel de l'exception. Ce bug existait depuis le début du projet mais n'avait jamais été visible : aucune route n'avait encore été *supprimée* pendant que l'app tournait avec un test dessus, donc `NoResourceFoundException` n'avait jamais eu l'occasion d'être levée. C'est précisément en écrivant le test de non-régression pour CET endpoint supprimé qu'il est apparu (500 au lieu du 404 attendu). Corrigé en ajoutant un `@ExceptionHandler(NoResourceFoundException.class)` dédié, plus spécifique, qui prend le dessus sur le handler générique.
Fichier : [GlobalExceptionHandler.java](src/main/java/com/rdvmedic/rdv_api/exception/GlobalExceptionHandler.java)
